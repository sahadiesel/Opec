# ฝ่ายบุคคล (HR) — ภาพรวม workflow และแผนปรับปรุง (7 หัวข้อ)

เอกสารนี้เก็บข้อตกลงจาก stakeholder ไว้เป็นฐานออกแบบ UI/navigation และงานต่อเนื่องใน repo  
**สถานะ:** หัวข้อปรับปรุง **1–7 ระบุรายละเอียดครบแล้ว** — implement แนะนำทำทีละส่วนและทดสอบกับ stakeholder ระหว่างทาง (ดูข้อ 7 และหมายเหตุท้ายเอกสาร)  

**แนวคิด workflow (คงไว้ — สอดคล้องกับ repo ปัจจุบัน)**

| บทบาท | หน้าที่หลัก |
|--------|----------------|
| **HR Officer** | เตรียมข้อมูล |
| **HR Manager** | ตรวจ / อนุมัติ / ล็อกส่งต่อ |
| **Accounting / Finance** | ทำจ่ายเงินจริง |

หน้า payroll ในระบบอธิบาย flow แล้วว่า **HR เตรียม → HR Manager อนุมัติ → Finance จ่าย** และมีการล็อกงวดภายหลัง (ทั้ง worker payroll และ office payroll)

---

## สิ่งที่โอเคอยู่แล้วใน repo (คงทิศทาง)

1. **แยก Worker Payroll กับ Office Payroll ชัดเจน** — navigation และ data model แยกกัน; office มี run/line ของตัวเอง ไม่ผูก timesheet รายวันแบบคนงาน; worker เน้น Payroll Batches / รอบจ่าย มากขึ้น  
2. **Worker payroll มี workflow อนุมัติเป็น batch** — generate batch, approve ฝั่ง HR, prepare ฝั่ง finance, lock ภายหลัง; snapshot / audit / state transition ชัดขึ้น  
3. **เมนูและคำอธิบายเริ่มสะท้อนบทบาท** — HR Officer ตรวจรายละเอียดรายบุคคล, HR Manager อนุมัติ, Finance Officer เบิกจ่ายจริง  

---

## หัวข้อที่ควรปรับปรุง — ทั้ง 7 หัวข้อ

### 1) เปลี่ยน HR เมนูจาก “หมวดข้อมูล” เป็น “โต๊ะทำงานตามหน้าที่” ✅ (ระบุรายละเอียดแล้ว)

**ปัญหา:** เมนู HR ยังเป็นแนวทะเบียน/หมวดข้อมูลมากกว่างานที่ต้องทำ — officer/manager ต้องไล่หลายหน้าเองกว่าจะรู้ เช่น เดือนนี้พนักงานออฟฟิศกี่คนต้องจ่าย, ลูกจ้างกี่คน, แต่ละ wave ค้าง timesheet เท่าไร, ใครยังไม่พร้อมออกสลิป, รอบไหนพร้อมส่งบัญชี

**ทิศทาง:** เมนูที่ใช้ทุกวันควรเป็น **“งานที่ต้องทำวันนี้”** ไม่บังคับให้เริ่มจาก master data ก่อนเสมอ

**โครงเมนูที่เสนอ — 3 โซนหลัก**

| โซน | ผู้ใช้หลัก | เนื้อหา |
|-----|------------|---------|
| **A. งานเตรียมจ่าย** | HR Officer | คิวพนักงานออฟฟิศที่ต้องทำ payroll; คิวลูกจ้างที่ต้องรวม timesheet; คิวเอกสาร/ข้อมูลที่ยังไม่ครบ; คิวรอออกสลิป |
| **B. งานตรวจอนุมัติ** | HR Manager | งวด payroll พนักงานออฟฟิศที่รอ approve; งวด payroll ลูกจ้างที่รอ approve; wave ที่ยังมี timesheet ค้าง; รายการผิดปกติ/ยอดที่แก้มือ |
| **C. งานทะเบียนและฐานข้อมูล** | ทุกคนตามสิทธิ์ | พนักงานออฟฟิศ, ลูกจ้าง, ตำแหน่ง, เอกสาร, ตั้งค่า HR |

เมนูเดิมที่ยกตัวอย่างว่า “เชิงทะเบียน”: พนักงานสำนักงาน, ลูกจ้าง/คนงาน, ตำแหน่ง, เอกสาร, ประวัติลงเวลา, จ่ายเงินเดือน, periods — ควรจัดเข้าโซน C หรือลิงก์รองจากโต๊ะงานในโซน A/B ตามบริบท

**สถานะ implement (baseline HR-D1):** Sidebar กลุ่ม **งานบุคคล (HR — โต๊ะทำงาน)** แบ่ง 3 โซนตามตาราง (เตรียมจ่าย / อนุมัติ / ทะเบียน) พร้อมคำอธิบายบทบาทใต้หัวโซน — มีหน้า `/hr/payroll-workbench` (แผนที่ลิงก์ + 3 คำถามหลัก) และ `/hr/payroll-approval` (จุดเข้าอนุมัติ + `#pending`) — ลิงก์คำขอแก้ไขไป `/hr/dashboard#hr-action-queue` (การ์ดคิวมี `id="hr-action-queue"`)

### 2) ต้องมี “Payroll Workbench” กลางใน HR ✅ (ระบุรายละเอียดแล้ว)

**ปัญหา:** มีทั้ง worker payroll และ office payroll แล้ว แต่ยังไม่มี **หน้าเดียว** ที่ตอบคำถามสำคัญสำหรับฝ่ายบุคคล เช่น

- เดือนนี้ต้องทำ payroll กี่คน (รวม / แยกออฟฟิศ vs ลูกจ้าง)
- ลูกจ้างแยกตาม wave จริงกี่คน
- timesheet ขาดกี่ใบ
- batch ไหนยังไม่ approve
- batch ไหนพร้อมส่งบัญชี

**ทิศทาง:** หน้าใหม่ชื่อประมาณ **HR Payroll Workbench** หรือ **ศูนย์งานจ่ายเงิน HR** — ให้ manager (และ officer) เห็นสถานะทันทีโดยไม่ต้องไล่หลายเมนู

**โครงหน้า — 4 บล็อกหลัก**

| บล็อก | ชื่อ | สิ่งที่ควรแสดง (spec) |
|--------|------|------------------------|
| **1** | **Office Staff Payroll Queue** | จำนวนพนักงานออฟฟิศ **active** ที่เข้า payroll เดือนนี้; กี่คนยังไม่มีข้อมูลธนาคาร; กี่คนยังไม่ครบเลขภาษี/ประกันสังคม; **งวด office payroll ล่าสุด**สถานะอะไร |
| **2** | **Worker Payroll Queue** | จำนวนลูกจ้างที่มีสิทธิ์จ่ายในรอบนี้; จำนวน wave ที่ active; **แต่ละ wave** มีคนกี่คน; timesheet **ครบ/ไม่ครบ** กี่คน (หรือสรุปตาม wave) |
| **3** | **Pending Approval** | **Office payroll runs** รอ manager approve; **Worker payroll batches** รอ manager approve; **correction requests** รอพิจารณา |
| **4** | **Ready for Finance** | งวดที่ **HR approve แล้ว**; จำนวนสลิปที่พร้อมออก; **ยอดรวมที่พร้อมส่งบัญชี** (ตาม scope ที่ระบบรองรับ) |

**ความสัมพันธ์กับข้อ 1:** หน้านี้เป็น **หัวใจของโซน A + B** (เตรียมจ่าย + รออนุมัติ) และเชื่อมต่อ **ส่งต่อ Finance** (โซน B/C ฝั่ง handoff) — เมนู HR ควรลิงก์มาที่นี่เป็น entry หลักของงานจ่ายเงิน

### 3) แยก workflow “ลูกจ้าง” กับ “พนักงานออฟฟิศ” ให้ชัดใน UI ✅ (ระบุรายละเอียดแล้ว)

**สถานะ backend:** โครงระบบรองรับแนวคิดแยกสองสายแล้ว แต่ **UI ยังไม่ทำให้เข้าใจง่ายพอ** — ผู้ใช้ยังสับสนได้ถ้าใช้คำรวม ๆ หรือ layout ไม่แยกสายชัด

**สองสายงาน (ต้องสื่อใน UI เหมือนกัน)**

| | **พนักงานออฟฟิศ (Office)** | **ลูกจ้าง / คนงาน (Worker)** |
|---|---------------------------|--------------------------------|
| **Timesheet** | ไม่ใช้ daily timesheet | ใช้ **timesheet รายวัน** |
| **งวดจ่าย** | **Monthly payroll run** | รวมตาม **period + wave** แล้วค่อย **generate payroll batch** |
| **การคำนวณ** | ฐานเงินเดือน + allowance + deduction → เข้า **office payroll** โดยตรง | ต้องเห็น **สถานะ timesheet ก่อนจ่าย** |

**สิ่งที่ควรปรับ (UI)**

- หน้า **HR Dashboard** และ **Payroll Workbench** (ข้อ 2) ต้องแยก **2 คอลัมน์หรือ 2 แพนเวลชัด:** **Office Payroll** | **Worker Payroll** — ไม่เรียงรวมเป็นบล็อกเดียวโดยไม่มีป้ายสายงาน  
- **หลีกเลี่ยงภาษารวม ๆ** อย่างเดียว เช่นแค่ “จ่ายเงินเดือน” โดยไม่บอกว่าเป็นสายออฟฟิศหรือสายคนงาน — ใช้ป้าย/หัวข้อที่ระบุสายงานเสมอ (เช่น “Office payroll run”, “Worker payroll batch”, “งวดพนักงานออฟฟิศ”, “รอบจ่ายลูกจ้าง”)  
- คำอธิบายสั้น (tooltip หรือ subtitle) ควรสะท้อนตารางด้านบนให้ผู้ใช้ใหม่ไม่สับสน  

**ความสัมพันธ์กับข้อ 2:** บล็อก 1–2 ของ Workbench จัดแยกอยู่แล้วตาม office vs worker — ต้องคง **ภาษาและ layout แยกคอลัมน์** ให้สอดคล้องกับข้อนี้ทุกหน้าที่เกี่ยวกับ payroll ใน HR  

**สถานะ implement (baseline HR-D3):** มีคอมโพเนนต์ `PayrollScopeTag` (`src/components/hr/payroll-scope-tag.tsx`) — ป้าย **Office Payroll** / **Worker Payroll** / **ทั้งสองสาย** บนหน้าที่เกี่ยวข้อง; เมนู HR ใน sidebar แยกหมวด **Office Payroll — รายเดือน** กับ **Worker Payroll — Timesheet & รอบจ่าย** ไม่ปน; แดชบอร์ด HR และทางลัดหน้าแรกแยกการ์ด/กลุ่มทางลัดตามสาย

### 4) Timesheet ของลูกจ้างต้องทำให้ง่ายกว่านี้ ✅ (ระบุรายละเอียดแล้ว)

**บริบทโลกจริง (ตามที่อธิบาย):** ลูกจ้างลงกระดาษ → ออฟฟิศได้กระดาษกลับมาแล้วคีย์ — ต้องรู้ว่าใครลงงาน/ไม่ลง, วันที่ลงเป็น normal / OT / ประเภทอื่น, และต้อง**รวมได้ง่ายตาม wave**

**สถานะ repo:** ฝั่ง timesheet เดินทิศถูกแล้ว — มี bulk generation / cloning ตาม wave และเน้น batch processing สำหรับ manpower scale สูง

**ช่องว่าง UX (แนะนำเพิ่ม):** ควรมีหน้า **“ลงเวลาแบบ batch ตาม wave”** เป็นมุมหลักสำหรับคนคีย์จากกระดาษ — **ไม่ให้คิดแบบรายคนรายวันก่อน**

**Flow ที่เสนอ — officer เข้า page เดียว แล้วเลือกฟิลเตอร์:**

- **Period**  
- **Wave**  
- **Customer**  
- **วันที่** (หรือช่วงวันที่ตามดีไซน์จอ)

จากนั้นเห็น **รายชื่อ worker ทั้งหมดใน wave นั้น** แล้วติ๊ก/กรอกได้ทันทีว่าแต่ละคน-แต่ละวัน (หรือแถวต่อวัน):

- ไม่ลงงาน  
- ลงงาน **normal**  
- มี **OT**  
- **standby**  
- **bump**  
- **remark**  

**เป้าหมาย:** คีย์จากกระดาษได้**ไว** — ไม่ต้องเข้า profile หรือเปิด record **ทีละคน**

**สถานะสี (ควรชัดใน UI)**

| สี | ความหมาย (spec) |
|----|------------------|
| **เขียว** | ลงครบ |
| **เหลือง** | ยังไม่ครบทุกวัน |
| **แดง** | ไม่มี timesheet / ข้อมูลผิด / เอกสารยังไม่ verify |

**Summary ต่อ wave (ควรมี)**

- คนทั้งหมด  
- ลงครบแล้วกี่คน  
- ค้างกี่คน  
- พร้อม payroll กี่คน  

**ความสัมพันธ์กับข้ออื่น:** สอดคล้อง **Worker Payroll Queue** ใน Payroll Workbench (ข้อ 2) และการแยกสาย worker ใน UI (ข้อ 3) — ข้อมูล timesheet ตาม wave เป็น input ก่อน generate batch

### 5) HR Officer ควร “เห็นราคาได้ แต่แก้ไม่ได้” ✅ (ระบุรายละเอียดแล้ว)

**เหตุผล:** ในงาน payroll ฝ่าย **officer ต้องรู้** เพื่อตรวจยอดได้ — ถ้าไม่เห็นจะ verify ไม่ได้ แต่ **ไม่ควรแก้** เพราะกระทบต้นทุนและความถูกต้องของระบบ

**ข้อมูลที่ officer ต้องมองเห็นได้ (ตัวอย่างจาก stakeholder):**

- **Rate ค่าจ้าง**  
- **Labor cost term**  
- **เงื่อนไข OT**  
- **Allowance ที่เกี่ยวข้อง**  

**สิทธิ์ที่ควรมี — HR Officer (แนวทาง)**

| อนุญาต (view) | ไม่อนุญาต (no edit / no elevated action) |
|----------------|--------------------------------------------|
| View **labor cost terms** | Edit labor cost terms |
| View **worker payment profile** | Edit **rate conditions** |
| View **payroll calculation breakdown** | **Approve** final batch |
| | **Unlock** locked payroll |

**ความสัมพันธ์กับ workflow:** สอดคล้องกับที่ repo สื่อ — **ฝ่ายบุคคลเตรียม → manager approve → finance pay**; officer เห็นตัวเลขเพื่อตรวจความสมเหตุสมผล แต่การเปลี่ยนอัตรา/เงื่อนไขและการอนุมัติ/ปลดล็อกอยู่ที่บทบาทสูงกว่า  

**หมายเหตุ implement:** ต้องสอดคล้องทั้ง **Firestore rules**, **`permissions.ts` / module keys**, และ **UI** (แสดง read-only + ซ่อน/disable ปุ่มแก้ไข) ไม่ใช่แค่ซ่อนเมนู

### 6) HR Manager ต้องมี “หน้าอนุมัติ” ที่ไม่ใช่แค่ dashboard สวย ✅ (ระบุรายละเอียดแล้ว)

**ปัญหา:** HR Manager เห็น dashboard / role command กว้าง แต่สำหรับงานจริงต้องมีหน้าที่ตอบคำถาม**เชิงควบคุม**ได้ทันที ไม่ใช่แค่ภาพรวมสวย ๆ

**คำถามที่หน้าอนุมัติควรตอบได้ (ตัวอย่าง):**

- Office payroll **รอบนี้มีกี่คน** / worker payroll **รอบนี้กี่คน**  
- **Wave ไหนยังไม่ครบ** (timesheet / ข้อมูล)  
- รายการไหนมีการ **override**  
- **ใครแก้หลัง verify**  
- **Batch ไหนรออนุมัติ**  
- **ยอดรวมเท่าไร** (gross / deduction / net ตาม scope)  
- **พร้อมส่งบัญชีหรือยัง**  

**หน้าใหม่ที่เสนอ — Payroll Approval Center**

- แยก **2 tab:** **Office Payroll Runs** | **Worker Payroll Batches**  

**แต่ละรายการในรายการ (row / card) ควรแสดงอย่างน้อย:**

- **Period**  
- **จำนวนคน**  
- **จำนวนสลิป**  
- **Gross / deduction / net**  
- **Status**  
- **Missing items** (สิ่งที่ยังไม่ครบ)  
- **Corrected items** (รายการที่แก้ไขแล้ว / ต้องติดตาม)  
- **Evidence completeness** (ความครบถ้วนของหลักฐานตามนโยบาย)  

**Actions ที่ต้องชัด (primary workflow):**

- **Review**  
- **Approve**  
- **Send back for correction**  
- **Lock & handoff to finance**  

**ความสัมพันธ์กับข้ออื่น:** ทับซ้อนกับ **Payroll Workbench** (ข้อ 2) โดยเฉพาะบล็อก **Pending Approval** และ **Ready for Finance** — Workbench = ภาพรวมทั้งฝั่ง officer/manager; **Approval Center** = จุดทำงานลึกของ manager โฟกัสอนุมัติและส่งต่อบัญชีโดยตรง

### 7) ควรลดเมนูซ้ำและ rename ให้ตรงงาน ✅ (ระบุรายละเอียดแล้ว)

**ปัญหา:** เมนูฝั่ง HR ยังมีคำที่ผู้ใช้ต้อง**ตีความเอง** — ไม่สื่อว่าเข้าไปแล้ว**จะทำงานอะไร**

**หลักการ:** ชื่อเมนูที่ดีต้องทำให้คนรู้ว่า **“เข้าหน้านี้ไปทำอะไร”** — ลดซ้ำซ้อนระหว่างเมนู และ **rename ให้เป็นงาน (task-oriented)** ไม่ใช่แค่ชื่อหมวดข้อมูล

**ตัวอย่างการเปลี่ยน (จาก stakeholder — ปรับได้ตาม UAT):**

| เดิม (ตัวอย่างจากภาพ) | แนวทางใหม่ (อ่านเป็นงาน) |
|------------------------|---------------------------|
| ประวัติลงเวลารายวัน | **คีย์ Timesheet** / **ตรวจ Timesheet** (หรือแยกสองทางเข้าถ้าจำเป็น) |
| จ่ายเงินลูกจ้าง | **งวดจ่ายลูกจ้าง** |
| งวด / รอบบัญชี | **รอบจ่ายเงินและตัดยอด** |
| พนักงานสำนักงาน | **ทะเบียนพนักงานออฟฟิศ** |
| ลูกจ้าง / คนงาน | **ทะเบียนลูกจ้าง** |

**งานที่เหลือหลัง rename:** ไล่ตรวจเมนู HR ทั้งหมดว่ามีลิงก์ซ้ำหรือชื่อคลุมเควหรือไม่ — จัดกลุ่มให้สอดคล้องโซน **งานเตรียมจ่าย / อนุมัติ / ทะเบียน** (ข้อ 1)

**แนวทาง rollout (สำคัญ):** เมื่อได้คอนเซ็ปทั้งหมดแล้ว **ค่อย ๆ เรียงทำทีละส่วน** — **อย่ารื้อทั้งระบบมากเกินไป** ปรับปรุงทีละส่วน แจ้ง stakeholder (เช่น พี่โจ้) **ให้ทดสอบก่อน** ถ้าโอเคค่อยทำส่วนถัดไป

## แผนแตกงาน (แจ้งพี่โจ้ — ตาม UAT ทีละส่วน)

แบ่งเป็น **7 งานหลัก (deliverables)** สอดคล้องหัวข้อ 1–7 ด้านบน — แต่ละงานทำเสร็จแล้วให้พี่โจ้ลองใช้/ทดสอบก่อนเริ่มงานถัดไป เพื่อเช็กว่าไม่หลุดจากแนวที่วางไว้

| ลำดับ | รหัส | งานที่ส่งมอบ (สรุป) | อ้างอิงหัวข้อในเอกสาร |
|------|------|---------------------|-------------------------|
| 1 | **HR-D1** | จัดโครงเมนู HR เป็น 3 โซน: งานเตรียมจ่าย (A) / งานตรวจอนุมัติ (B) / ทะเบียนและฐานข้อมูล (C) + ลิงก์ entry หลัก | ข้อ 1 |
| 2 | **HR-D2** | หน้า **HR Payroll Workbench** (ศูนย์งานจ่ายเงิน HR) — 4 บล็อก: Office queue, Worker queue, Pending approval, Ready for finance | ข้อ 2 |
| 3 | **HR-D3** | บน Dashboard / Workbench: แยก **2 คอลัมน์หรือแพนเวลชัด** Office Payroll \| Worker Payroll + ปรับภาษาไม่ใช้คำรวมอย่างเดียว | ข้อ 3 |
| 4 | **HR-D4** | หน้า **ลงเวลาแบบ batch ตาม wave** (ฟิลเตอร์ period / wave / customer / วันที่ + กริดติ๊ก/กรอก + สีสถานะ + summary ต่อ wave) | ข้อ 4 |
| 5 | **HR-D5** | **HR Officer** เห็น rate / labor cost / OT / allowance / breakdown ได้ แต่แก้ไม่ได้ — Firestore rules + `permissions` + UI read-only; ห้าม approve batch / unlock | ข้อ 5 |
| 6 | **HR-D6** | หน้า **Payroll Approval Center** — 2 แท็บ Office runs \| Worker batches + คอลัมน์ครบ + actions: review / approve / send back / lock & handoff | ข้อ 6 |
| 7 | **HR-D7** | **Rename เมนู + ลดซ้ำ** ตามตารางข้อ 7 + ไล่ตรวจเมนู HR ทั้งชุด | ข้อ 7 |

**ลำดับที่แนะนำสำหรับพัฒนา (ปรับได้ตามทรัพยากร):** D1 → D2 → D3 → D6 → D4 → D5 → D7  
- เหตุผล: โครงนำทางและ Workbench มาก่อน แล้วค่อยขยาย Approval Center (manager) จากนั้นค่อย timesheet batch (ใช้เวลาพัฒนานาน) และสิทธิ์ officer — ปิดท้าย rename เมื่อ flow นิ่งแล้วจะไม่ต้องเปลี่ยนชื่อซ้ำ  

**หมายเหตุ:** D2 กับ D3 อาจรวมเป็นรอบเดียวถ้าทีมพัฒนาส่งพร้อมกันได้ — แต่แยกรหัสไว้ให้พี่โจ้ตรวจทีละเรื่องได้ชัด

### ข้อความส่งพี่โจ้ (ร่าง)

> พี่โจ้ครับ ทางทีมจะทำปรับปรุงฝ่ายบุคคล / payroll ตามเอกสาร `docs/hr-payroll-workbench-roadmap.md` โดยแบ่งเป็น **7 งานหลัก (HR-D1 … HR-D7)** ตามตารางในเอกสาร  
> แต่ละงานทำเสร็จจะแจ้งให้พี่โจ้ **ลองใช้ทีละส่วน** ก่อนเริ่มงานถัดไป เพื่อดูว่าตรงแนวที่วางไว้หรือมีจุดที่ต้องแก้คำ/flow เพิ่ม  
> ถ้าพี่โจ้สะดวก รบกวนเก็บ feedback ต่อรอบว่า “ผ่าน / ต้องปรับ …” จะได้ไม่หลุดจากคอนเซ็ป officer เตรียม → manager อนุมัติ → finance จ่าย

## หมายเหตุสำหรับการ implement ภายหลัง

- ไม่เปลี่ยนแนวคิด **Officer เตรียม → Manager อนุมัติ/ล็อก → Finance จ่าย**  
- โครงสร้างข้อมูล payroll แยก worker/office และ batch workflow **ไม่ต้องทุบ** — เน้นปรับ **การค้นพบงาน (discoverability)** และ **navigation ตามบทบาท**  
- **หัวข้อปรับปรุง 7 ข้อระบุครบในเอกสารนี้แล้ว** — แตกเป็น **7 งานหลัก (HR-D1–D7)** ตามตารางด้านบน  
- **Rollout:** ทำทีละส่วน ทดสอบกับ stakeholder ระหว่างทาง หลีกเลี่ยงการเปลี่ยนทั้งเมนู/ทั้งระบบในครั้งเดียวโดยไม่จำเป็น
